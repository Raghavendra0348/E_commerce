# E-Commerce Bug Audit

Date: 4 November 2026

Follow-up: BUG-01 through BUG-10 have been fixed and regression-tested. See [how the fixes work and their verification results](BUG_FIXES_01_TO_10.md). The findings below retain the original audit descriptions; they are not a current list of unresolved issues.

Second follow-up, 7 November 2026: BUG-11 through BUG-20 are also fixed and verified. See [the per-bug explanations and verification report](BUG_FIXES_11_TO_20.md). The CI work also clears BUG-34's lint blocker; order-provider fields used by the COD/refund workflow now address BUG-33.

Scope: current working-tree frontend, backend, payment/order flows, authentication, deployment files and CI. This is a review of the application, not a review of the SRS draft. Existing uncommitted application changes were included in the review and preserved.

The review identified **34 issues**. This is the set identified in this review; it is not a guarantee that every possible defect has been discovered. Conditional deployment findings describe the configuration or environment that triggers them.

## Verification performed

- Existing frontend suite: **107 tests passed** across 27 files.
- Existing backend suite: **31 tests passed** across 10 files.
- Frontend production build: **passed**.
- Backend lint: **failed**, with four errors and one warning.
- Additional review checks: **17 backend reproduction scenarios and 10 frontend reproduction tests** completed, demonstrating faulty behaviour outside the existing test coverage.
- Deployment checks reproduced the missing production webhook-secret validation failure, missing CI environment validation failure, and shared production proxy identity.
- Order/concurrency checks used isolated temporary database fixtures. Payment gateway operations were replaced with a fake gateway; no real payment or refund was requested.
- Audit fixtures were removed: zero audit users/categories remained, and the catalog still contained 221 products.
- Application source was not changed to fix these issues. Temporary frontend test files were archived outside the active test directory.

Evidence labels: **R** = reproduced with executable checks; **S** = established by source/configuration inspection. Some findings combine reproduced behaviour with an inspected caller or deployment path. No live browser visual audit or actual Docker deployment was performed.

## Critical and high-priority issues

### BUG-01 — Critical — Production has publicly known default token-signing secrets [S]

Source: [docker-compose.yml](../docker-compose.yml), lines 34–35; [JWT utilities](../Backend/src/utils/jwt.utils.js).

When the deployment operator does not override the JWT variables, Compose supplies literal signing secrets from the repository. Anyone who knows those values can generate accepted access tokens, including an administrator role. These environment defaults also take precedence over values loaded by the application's normal dotenv configuration.

Fix direction: require explicitly supplied production secrets and fail startup when they are missing.

### BUG-02 — High — Docker copies the local backend environment file into the image [S]

Source: [Backend/Dockerfile](../Backend/Dockerfile), line 14. `Backend/.env` exists and `Backend/.dockerignore` is absent.

Building from this checkout includes the local environment file in the final backend image through `COPY . .`. The image therefore contains configured credentials. The Git ignore file does not exclude files from the Docker build context. Both application Docker contexts also lack ignore rules for host dependencies and other local artifacts.

Fix direction: add Docker ignore rules for environment files, host dependencies, logs and other local artifacts; supply runtime secrets through deployment configuration.

### BUG-03 — High — An old account's failed request can be retried as the new account [R]

Source: [Axios client](../Frontend/src/api/axios.js), lines 60–102.

Send an authenticated request as account A, switch to B, and then deliver A's expired-token response. The interceptor reads B's refresh token and retries A's original request body with B's new access token. The reproduction retried A's address-creation payload as B. The session check starts when refresh begins, rather than when the original request was issued.

Fix direction: attach the originating session revision to each request and reject retries after an account change.

### BUG-04 — High — Demoted administrators retain access through existing access tokens [R]

Source: [authentication middleware](../Backend/src/middleware/auth.middleware.js), lines 20–22; [admin middleware](../Backend/src/middleware/admin.middleware.js), line 8; [role updates](../Backend/src/services/admin.service.js).

An administrator token was still accepted by both middleware functions after its owner's database role changed to USER. Permissions are taken entirely from the old token until it expires. Password changes and logout-all similarly revoke refresh tokens without invalidating already-issued access tokens.

Fix direction: validate current permissions/session revocation using a server-side session or user token version.

### BUG-05 — High — Cart quantity and delete actions use the wrong identifier [R]

Source: [CartItem](../Frontend/src/components/cart/CartItem.jsx), lines 39–43; [cart store](../Frontend/src/store/useCartStore.js), lines 51–64; [cart routes](../Backend/src/routes/cart.routes.js).

The UI passes `CartItem.id`, while the API interprets the path as `productId`. A fixture with cart row 84 and product 244 failed with "Item not in cart". Frontend checks also confirmed that quantity/delete requests used the row ID. If that number matches a different product in the user's cart, the wrong product can be changed or removed.

Fix direction: use the product ID for these API operations, while retaining cart row IDs for selection and selected-item checkout.

### BUG-06 — High — Simultaneous checkout requests create duplicate orders [R]

Source: [order service](../Backend/src/services/order.service.js), lines 36–38 and 68–124.

Two requests can read the same cart before either transaction removes its rows. Both then create an order and decrement stock. The second request does not check whether its cart-row deletion actually removed anything. The reproduction created two successful COD orders from one cart item and reduced stock from 20 to 18.

Fix direction: claim the cart selection inside the transaction and enforce checkout idempotency.

### BUG-07 — High — Concurrent cancellations restore stock twice [R]

Source: [order service](../Backend/src/services/order.service.js), lines 183–224 and 250–292.

Cancellation eligibility is checked before the transaction. Two requests can both read an eligible order and each restore its inventory. A one-unit order produced two successful cancellation responses and a two-unit stock increase. The admin cancellation path uses the same unsafe pattern.

Fix direction: make the state transition conditional and restore inventory only for the request that successfully changes the state.

### BUG-08 — High — A late payment webhook reopens a cancelled order [R]

Source: [payment service](../Backend/src/services/payment.service.js), lines 229–254.

The payment-captured handler updates the order to CONFIRMED without checking its current fulfilment state. Cancelling a fixture and then delivering its signed payment-captured event changed it back to CONFIRMED after inventory had already been restored.

Fix direction: reconcile late payment against the current order state and enter the appropriate refund/review flow without reopening fulfilment.

### BUG-09 — High — Payment retries overwrite the previous gateway order [R]

Source: [payment service](../Backend/src/services/payment.service.js), lines 16–34 and 72–73; [PaymentButton](../Frontend/src/components/checkout/PaymentButton.jsx).

Every payment attempt creates a new gateway order and overwrites the only stored gateway identifier. After a retry, a correctly signed payment from the earlier attempt is rejected as a mismatched order. Its capture webhook also cannot find the overwritten identifier. This can leave a customer charged while the application still considers the order unpaid.

Fix direction: reuse an outstanding gateway order or retain separate immutable payment-attempt records.

### BUG-10 — High — Failed webhook processing is acknowledged as successful [R]

Source: [webhook controller](../Backend/src/controllers/webhook.controller.js), lines 32–41.

A simulated database failure during a valid payment event still returned HTTP 200 with `{ received: true }`. The payment remained PENDING. The controller suppresses the failure without durable retry/reconciliation, so the provider is told that an unprocessed event succeeded.

Fix direction: acknowledge only after durable acceptance; retry transient processing failures through an appropriate response or a durable event queue.

### BUG-11 — High — Product deletion fails for cart/wishlist references and can remove images first [R + S]

Source: [product service](../Backend/src/services/product.service.js), lines 265–296; [database schema](../Backend/prisma/schema.prisma).

Deletion checks order references but ignores restrictive cart and wishlist foreign keys. A product referenced by a temporary cart could not be deleted. Cloudinary image deletion happens before the database delete, so a failed deletion can leave the retained product pointing to deleted photos. The foreign-key failure was reproduced; no real image was deleted during this audit.

Fix direction: resolve or reject all blocking references before deleting external assets, and use a recoverable deletion workflow.

### BUG-12 — High — Production customers share the proxy's rate-limit identity [R + S]

Source: [proxy configuration](../Backend/src/config/developmentProxy.js), line 3; [Nginx configuration](../Frontend/nginx.conf); [rate limiter](../Backend/src/middleware/rateLimiter.middleware.js).

Forwarded client addresses are trusted only in development. Behind the production Nginx proxy, different customers resolve to the proxy's IP and share its limits, including the stricter authentication limit. Two different forwarded client IPs resolved to the same address in the reproduction. The current general limit is 1,000 per 15 minutes; the authentication limit is 10.

Fix direction: configure narrowly scoped production proxy trust for the actual deployment topology.

### BUG-13 — High — Compose does not supply the required payment webhook secret [R + S]

Source: [docker-compose.yml](../docker-compose.yml), lines 30–37; [environment validation](../Backend/src/config/env.js), lines 25–49.

Compose supplies the payment key and secret but omits `RAZORPAY_WEBHOOK_SECRET`. On a clean build without a separately baked backend environment file, production startup fails validation. Defining the variable in Compose's interpolation environment does not pass it to this container unless it is wired into its environment. The isolated validation check exited with this exact missing-secret error. A copied local `.env` can mask the defect while causing BUG-02.

Fix direction: explicitly pass all required runtime settings, including the webhook secret and frontend origin.

### BUG-14 — High — A fresh container database is never migrated [S]

Source: [docker-compose.yml](../docker-compose.yml); [Backend/Dockerfile](../Backend/Dockerfile), lines 17–26; [server startup](../Backend/src/server.js).

The advertised one-command stack starts PostgreSQL and the backend without applying Prisma migrations. Client generation does not create database tables. With a new database volume, model-dependent requests fail until an operator manually runs migrations. The configured liveness probe can still succeed because it does not check the application schema.

Fix direction: add an explicit migration deployment step before serving application traffic.

### BUG-15 — High — Backend CI lacks the database and required test environment [R + S]

Source: [CI workflow](../.github/workflows/ci.yml), lines 9–38; [environment validation](../Backend/src/config/env.js); backend integration tests.

The backend job runs integration tests but defines no PostgreSQL service, database URL, JWT secrets or migration step. On a clean runner, the untracked local environment file is unavailable. An isolated environment check failed on DATABASE_URL, JWT_SECRET and JWT_REFRESH_SECRET. Even after the lint errors are fixed, this test job is incomplete.

Fix direction: provision an isolated CI database, apply migrations and provide non-production test settings.

## Medium-priority application issues

### BUG-16 — Medium — Multiple tabs can invalidate each other's login sessions [R + S]

Source: [auth store](../Frontend/src/store/useAuthStore.js), lines 9–19 and 50–68; [Axios refresh](../Frontend/src/api/axios.js), lines 14–15 and 60–83; [token rotation](../Backend/src/services/auth.service.js), lines 124–157.

Tabs share persisted refresh tokens, but each keeps its own in-memory copy and refresh lock. After one tab rotates a token, another can reuse the old token and trigger theft detection, revoking the first tab's replacement too. That revocation sequence was reproduced. There is no cross-tab token synchronization or refresh coordination.

Fix direction: coordinate rotation between tabs and synchronize authentication changes.

### BUG-17 — Medium — Delivered COD orders have no payment reconciliation path [R + S]

Source: [order status update](../Backend/src/services/order.service.js), line 295; [payment routes](../Backend/src/routes/payment.routes.js); [dashboard revenue](../Backend/src/services/admin.service.js), lines 12–15.

Delivering a COD fixture left both its order and payment at PENDING. There is no dedicated API/admin action to record cash collection. Such orders remain unpaid in the application and are excluded from paid-revenue statistics.

Fix direction: add an authorised cash-collection operation and synchronize the order/payment records.

### BUG-18 — Medium — Paid-order cancellation does not actually start the refund [S]

Source: [cancellation](../Backend/src/services/order.service.js), lines 197–213; [refund API](../Backend/src/routes/payment.routes.js), line 17; [admin orders](../Frontend/src/pages/admin/AdminOrders.jsx); [frontend payment service](../Frontend/src/services/payment.service.js).

Cancellation sets REFUND_PENDING, but neither cancellation path calls the refund function. The admin UI and frontend payment service have no refund-submission action. Normal customer/admin UI usage therefore leaves the refund pending without a gateway request, despite customer-facing wording saying it is being processed. The backend endpoint can be invoked manually.

Fix direction: connect cancellation to a reliable refund workflow or provide the explicit administrative action and accurate status wording.

### BUG-19 — Medium — Refund submission accepts the wrong order state and does not set pending [R]

Source: [refund service](../Backend/src/services/payment.service.js), lines 125–184.

The endpoint checks payment status but never verifies that the order is cancelled, although its route/controller describe a cancelled-order refund. A DELIVERED/PAID fixture was accepted by the fake gateway. Successful submission also left its payment status PAID because no pending-state update is performed on the success path.

Fix direction: validate order eligibility and atomically record the refund request/status before submitting it.

### BUG-20 — Medium — Failed refunds cannot be retried through the refund endpoint [R]

Source: [refund service](../Backend/src/services/payment.service.js), lines 129–132 and 150–170.

A simulated temporary gateway failure sets REFUND_FAILED. The endpoint then rejects a retry because it accepts only PAID or REFUND_PENDING. The operator has no supported retry transition through this API.

Fix direction: allow controlled retries with attempt tracking and duplicate-refund protection.

### BUG-21 — Medium — Delayed refund events can overwrite completed refunds [R]

Source: [refund webhook handling](../Backend/src/services/payment.service.js), lines 288–309.

Delivering a signed refund-failed event to a fixture already marked REFUNDED changed it to REFUND_FAILED. The handler tracks only payment ID and current equality with the incoming status; it does not protect completed outcomes or distinguish refund attempts.

Fix direction: track refund IDs/attempts and apply valid state transitions when events arrive late or out of order.

### BUG-22 — Medium — Product-detail wishlist state disagrees with the server [R]

Source: [ProductDetail](../Frontend/src/pages/ProductDetail.jsx), lines 73 and 148–158.

The detail page starts with `wishlisted = false`, does not read the shared wishlist, and ignores the server's toggle result. When the server returned `action: removed`, the page displayed "Saved to Wishlist" and showed a saved-success toast. Catalog/wishlist cards use a different shared implementation.

Fix direction: use the shared wishlist hook and server-confirmed state on product details.

### BUG-23 — Medium — Guest Buy Now loses the selected product [R]

Source: [ProductDetail](../Frontend/src/pages/ProductDetail.jsx), lines 131–134; [Login](../Frontend/src/pages/Login.jsx), lines 42–50.

A guest's Buy Now action goes to sign-in with `/checkout` as the return destination, without adding or retaining the selected product. After sign-in, an empty cart cannot check out; an existing cart contains different items. Catalog cards correctly return guests to the selected product instead.

Fix direction: preserve the intended product purchase across authentication.

### BUG-24 — Medium — Buy Now does not select a previously unchecked product [R]

Source: [purchase action](../Frontend/src/hooks/useProductCartAction.js), lines 27–29; [cart selection](../Frontend/src/store/useCartStore.js), lines 9–11 and 32.

Uncheck a cart product, then press Buy Now for the same product. The cart quantity is increased, but its existing cart-row exclusion is preserved. The reproduction navigated to checkout with zero selected items, excluding the product just requested for purchase.

Fix direction: explicitly select the purchased product before entering checkout, with a defined policy for other selected items.

### BUG-25 — Medium — Cart load failures are hidden as empty/successful results [R]

Source: [cart store](../Frontend/src/store/useCartStore.js), lines 34–36 and 42–45; [purchase action](../Frontend/src/hooks/useProductCartAction.js), lines 27–30.

`fetchCart()` catches errors and returns null without storing an error state. Cart screens can show "empty" after a failed initial load. Add/Buy Now treats that null refresh as success. A reproduced failed cart read still navigated to checkout with no loaded cart and no error notification.

Fix direction: expose a retryable cart error and let dependent actions detect refresh failures.

### BUG-26 — Medium — Cart mutations can reuse a stale read from before the write [R]

Source: [cart store](../Frontend/src/store/useCartStore.js), lines 21–22 and 42–64.

If a background cart GET is already running, an add/update/remove action reuses its promise after the write. That GET can contain the old cart snapshot. The reproduction completed an add but restored an empty cart with only one GET performed. Visible cart contents/counts can stay stale until another refresh.

Fix direction: invalidate reads that predate a mutation or consume the mutation's returned cart.

### BUG-27 — Medium — An old clear-cart response clears the next account's visible cart [R]

Source: [cart store](../Frontend/src/store/useCartStore.js), lines 70–73.

Start clearing account A's cart, sign in as B and load B's cart, then finish A's request. The unguarded response resets B's in-memory cart/count to empty. The reproduction confirmed this state loss; it does not imply B's database cart was deleted by that old response.

Fix direction: guard mutation completions with the originating session revision.

### BUG-28 — Medium — Product APIs omit the ratings expected by cards and detail headings [R + S]

Source: [product API service](../Backend/src/services/product.service.js), lines 43–57 and 72–101; [card rating](../Frontend/src/components/product/ProductCardParts.jsx), lines 72–73; [detail rating](../Frontend/src/pages/ProductDetail.jsx), lines 206–220.

Product responses contain neither `avgRating` nor `reviewCount`. A product with a real temporary review still lacked both fields. The card and main detail heading therefore hide their rating display, while the separately fetched reviews section can show ratings.

Fix direction: include consistent review aggregates in the product response or obtain them through an appropriate query.

### BUG-29 — Medium — Product-detail Add to Cart and Buy Now can submit together [R]

Source: [ProductDetail](../Frontend/src/pages/ProductDetail.jsx), lines 71–72, 302 and 323.

The two purchase buttons maintain separate pending flags. Starting Add to Cart leaves Buy Now enabled; clicking it submits a second cart request before the first finishes. This was reproduced. Catalog cards already use a shared purchase guard.

Fix direction: share a single pending guard across product-detail purchase actions.

### BUG-30 — Low — Fractional stock and category IDs are silently truncated [R]

Source: [product validation](../Backend/src/validators/product.validator.js), lines 23–35 and 62–73.

The validator uses `parseInt` before checking validity. Stock `"1.9"` was accepted as 1, and a fractional category ID was accepted as its integer prefix. Invalid API data can be saved with unintended values rather than rejected.

Fix direction: require finite integers before accepting stock and identifiers.

### BUG-31 — Low — Cancellation returns the pre-cancellation order [R]

Source: [order service](../Backend/src/services/order.service.js), line 224.

The database was CANCELLED, but the returned order still said CONFIRMED. The service returns the object fetched before its transaction. Refetching masks this in the current UI, but API consumers receive contradictory state.

Fix direction: return the updated order/payment state from the transaction.

### BUG-32 — Medium — Storage failures break authentication state changes [R + S]

Source: [auth store](../Frontend/src/store/useAuthStore.js), lines 37–46, 85, 97 and 108–117.

Initial storage reads are caught, but later persistence/removal operations are not. A reproduced `localStorage.removeItem` failure caused logout to throw before clearing the authenticated in-memory state. Failed writes can similarly interrupt sign-in or token updates.

Fix direction: make storage operations best effort and always complete the corresponding in-memory auth transition.

### BUG-33 — Medium — Order lists omit or read nonexistent payment-method fields [R + S]

Source: [customer order query](../Backend/src/services/order.service.js), lines 148–154; [admin order query](../Backend/src/services/order.service.js), lines 240–242; [OrderCard](../Frontend/src/components/account/OrderCard.jsx), line 87; [admin order modal](../Frontend/src/pages/admin/AdminOrders.jsx), line 225.

List responses omit the payment relation, while OrderCard/admin views read `order.paymentMethod`, which is not an Order field. The backend reproduction confirmed that customer list rows expose neither field. COD badges disappear and the administrative payment-method value is blank. The detail endpoint uses the payment provider correctly.

Fix direction: include payment-provider information consistently and render the actual response contract.

### BUG-34 — Medium — Backend lint currently blocks the CI job [R]

Source: [download image script](../Backend/scripts/download-product-images.js), lines 48 and 96; [upload image script](../Backend/scripts/upload-product-images.js), lines 108 and 115; [CI lint step](../.github/workflows/ci.yml), line 34.

`npm.cmd run lint` exits unsuccessfully with four errors: two empty catch blocks and two rethrown errors that omit the caught cause. There is also an unused-variable warning in `expand-catalog.js`, line 207. Because lint runs before tests, backend CI stops at this step.

Fix direction: address the four lint errors; clean up the warning as part of the same maintenance change.

## Reproduction evidence

Local review artifacts are stored under the ignored directory `output/playwright/bug-audit/`:

- `backend-audit.cjs` and `backend-results.json`: database-backed service reproductions using fake gateway operations.
- `frontend-reproductions.test.jsx`: nine UI/store reproductions, archived after execution.
- `frontend-axios-reproduction.test.jsx`: the account-switch request-retry reproduction, archived after execution.
- `deployment-audit.cjs` and `deployment-results.json`: isolated environment-validation and proxy checks.

The frontend test archives retain imports relative to their temporary original location under `Frontend/src/test/`. They must be restored there to rerun them. Their assertions describe observed faulty behaviour; they are not permanent regression tests asserting corrected behaviour.

Recommended first fixes: BUG-01 through BUG-10, then product deletion and deployment/CI configuration. Keep security/session changes, checkout idempotency, inventory transitions and payment reconciliation covered by regression tests when fixing them.
